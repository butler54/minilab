# Phase 0 Research: Delivery Paths for CPU Reduction

**Date**: 2026-10-09 · **Branch**: `010-reduce-cpu-usage`

## D1 — Why the cluster never converged after feature 007

**Decision**: The leak is deleted as a one-time recorded imperative repair; no change to the parent app's sync policy.

**Finding**: Commit `e750ac1` ("switch to downstream Red Hat build via OLM subscription") removed `applications.agent-sandbox` from `values-prod.yaml`, but the live app-of-apps `minilab-prod` has `syncPolicy: {automated: {selfHeal: true}}` — **`prune` absent**. Live status confirms: `minilab-prod` is `OutOfSync` with a single drifted resource `Application/agent-sandbox`. The leaked Application still renders the upstream `kubernetes-sigs/agent-sandbox` Helm chart (`helm/` @ `v1.0.3`), creating `agent-sandbox-system/agent-sandbox-controller` with labels/selector from Helm — colliding with the OLM CSV's expected selector. ArgoCD shows it as `OutOfSync` forever but never deletes it.

**Leak blast radius** (`oc get application agent-sandbox -o jsonpath=.status.resources`): `Deployment/agent-sandbox-controller`, `ClusterRole/agent-sandbox-controller`, `ClusterRole/agent-sandbox-controller-extensions`, `ClusterRoleBinding/agent-sandbox-controller`. The four `agents.x-k8s.io` CRDs (created 2026-09-26, same minute) are **not tracked** — Helm `crds/` content is unmanaged by both Helm and ArgoCD — so deleting the Application cannot cascade into CRD removal. Zero `Sandboxes`/`SandboxClaims` CRs exist; the openshell demo is not currently holding sandbox state. Application finalizer `resources-finalizer.argocd.argoproj.io/foreground` cascades deletion to exactly the 4 tracked resources.

**Alternatives rejected**:
- *Enable `prune` on `minilab-prod`*: the app-of-apps is generated by the **patterns-operator** (`newArgoApplication`), not by chart values; its syncPolicy is operator-owned code, without a values seam, so any edit would be reverted by the operator reconcile. Also changes deletion semantics pattern-wide for a one-off leak — worse blast radius.
- *Re-add app to Git at a tombstone commit then remove*: would re-render the upstream chart (the helm source repo still exists) and deepen the conflict — dangerous.
- *Delete the CSV instead and keep the Helm copy*: contradicts feature 007's deliberate move to the Red Hat downstream build (test suites `test-external-refs.sh`/`test-openshell-render.sh`/`test-openshell-pins.sh` actively forbid the upstream chart returning).

## D2 — ArgoCD 600s: only the patterns-operator overlay survives reconciliation

**Decision**: Deliver `timeout.reconciliation: 600s` as `main.gitops.customArgoYaml` in `values-global.yaml`; apply with the framework's own idempotent `make operator-deploy` (rhvp.cluster_utils `operator_deploy` role + `pattern-install` 0.0.18). Verified against source:

- `patterns-operator/internal/controller/argo.go` `createOrUpdateArgoCD()` regenerates the `vp-gitops` ArgoCD CR spec from operator defaults on every reconcile and calls `Update` when `compareArgoCD` detects drift → **direct edits to the ArgoCD CR or `argocd-cm` are reverted** (second-order: the openshift-gitops operator owns `argocd-cm` from the ArgoCD CR).
- The same function deep-merges (`mergo.WithOverride`) `patternsOperatorConfig.gitops.customArgoYaml` over the generated spec, on both create and update paths (`applyCustomArgoOverlayToSpec` + `applyCustomArgoOverlay` in `internal/controller/argo.go`), config keys defined in `internal/controller/patterns_operator_config.go` (`configKeyCustomArgoYaml = "gitops.customArgoYaml"`).
- The `pattern-install` chart 0.0.18 templates `gitops.customArgoYaml` into `patterns-operator-config` ConfigMap when `main.gitops.customArgoYaml` is set (`templates/pattern-operator-configmap.yaml`) — this repo's `values-global.yaml` `main:` section is exactly the values file consumed by `make operator-deploy`.

**Chain**: `values-global.yaml` → ConfigMap `patterns-operator-config` → patterns-operator → ArgoCD CR `vp-gitops` `spec.extraConfig["timeout.reconciliation"]="600s"`. The gitops operator then writes `argocd-cm`. Contract: `contracts/argocd-cadence-contract.md`.

**Notable collateral**: patterns-operator's generated ArgoCD spec already grants the controller `Limits: 2 CPU / Requests: 250m` — cadence changes don't need resource edits.

## D3 — Platform monitoring has no scrape-interval knob in OCP 4.22 (user's "60s for cluster monitoring" needs a translation)

**Decision**: Use `prometheusK8s.collectionProfile: minimal` in `cluster-monitoring-config`, delivered by a new local Helm chart; honor 60s exactly where it *is* supported (pattern-owned scrape surfaces).

**Finding**: Fetched the live CMO `Documentation/api.md` for `release-4.22`:
- `PrometheusK8sConfig` (platform) exposes: retention, retentionSize, resources, `collectionProfile`, tolerations… — **no `scrapeInterval`/`evaluationInterval`**.
- `PrometheusRestrictedConfig` (**user workload** monitoring only) exposes `scrapeInterval` (5s–5m) — but enabling UWM deploys a second platform Prometheus+thanos-ruler stack, a heavier change rejected under Principle IV.
- `collectionProfile` description: *"In the `minimal` profile, Prometheus only collects metrics necessary for the default platform alerts, recording rules, telemetry and console dashboards."* — preserves alerting and console dashboards while cutting series volume and platform Prometheus CPU/database work substantially. This is the largest supported lever for the user's stated goal.

**Where 60s applies directly**: 
- `charts/observability-config/templates/scrape-configs.yaml` external-target `ServiceMonitor` endpoints get `interval: {{ $obs.scrapeInterval | default "30s" }}` — new `global.observability.scrapeInterval: 60s` knob in `overrides/values-observability.yaml`.
- The `minilab` MonitoringStack Prometheus is only 9m CPU — tuning here satisfies the user's "60s" directive precisely but yields little CPU; the big win is D4.

**Deviate-and-document**: "60s for cluster monitoring config" is not expressible for platform Prometheus in OCP 4.22. The plan delivers the *outcome* (measurably reduced monitoring CPU, FR-006, SC-006) via the supported mechanism, and the 60s cadence on pattern-owned scrapers. This deviation is called out in the spec assumptions and quickstart gate G5 verifies alerting/dashboard continuation.

## D4 — Monitoring config must not fight CMO

**Decision**: `cluster-monitoring-config` (namespace `openshift-monitoring`, pre-existing, currently empty) is managed **additively** by a new GitOps application `openshift-monitoring-config` (no namespace declaration needed — the namespace is platform-owned). The chart renders the full ConfigMap `data.config.yaml` from values so Git remains truth for the keys we own; any future platform-write to that CM would surface as drift (intentional carrier for Principle I).

**Rationale**: CMO treats this ConfigMap as user-input, not operator-managed state — it does not reconcile/overwrite it. Making GitOps owner of the user-provided config object is the standard OpenShift-as-Code pattern and follows Principle I.

**Alternatives rejected**: a `make`/`ansible-imperative` one-shot (config then drifts silently — violates Principle I); patching via MachineConfig (platform configs-as-files pattern — overkill, forbidden more machinery).

## D5 — No platform-cluster-monitoring Das `scrapeInterval` means alerting delay is bounded by defaults

60s-capability note for edge case in spec: `collectionProfile: minimal` **retains** the default 30s scrape for the metrics it keeps, so node-saturation / API alerts stay on the factory cadence. The spec edge case ("must preserve tight cadence for control-plane alerts") is satisfied by construction.

## D6 — Ancillary load deferral (monitor first, adjust after)

Unseal cronjob (`*/5`, 667MB image, image-cached), catalog polling (~26m CPU), kube-apiserver 295m etcd, etc. are each < 5% of the incident. Per user direction "monitor and incrementally adjust from there", they are **not** changed in this implementation; `quickstart.md` G6 contains the decision table for follow-up levers (unseal cadence reduction, catalog poll widening, COO resource sizing) only if SC-001/SC-007 remain unmet after D1–D4 land. This keeps the change set minimal and attribution clean per measurement philosophy in FR-011.

## D7 — Iterative test design

Test pyramid per user "iteratively test as part of the plan":

1. **Static (off-cluster, first)**: extend pattern test suites — new `tests/test-argocd-cadence.sh` (values carry 600s), `tests/test-monitoring-config.sh` (helm-rendered CM == contract); existing suites must stay green (`make validate-schema`, `test-external-refs.sh` still forbids upstream agent-sandbox chart, `test-openshell-render.sh`).
2. **Repair rehearsal**: script runs `--dry-run` probes first; actual deletion staged behind explicit confirmation counts-down resource list; post-run probes auto-collected.
3. **Live gates**: G1–G6 in quickstart.md, each with measurement (top-pod + PromQL probes from `ANALYSIS.md`), each gating the next change. Every gate appends evidence into `ANALYSIS.md` (FR-011).
4. **Soak**: G6 = 1h steady-state window + re-run of SC probes.
